## 1. 글꼴 로딩

### 1.1 측정

360px, 로컬 정적 서버, 느린 모바일 네트워크 에뮬레이션(1.6Mbps, RTT 150ms) + CPU 4배, 콜드 캐시, 5회 중앙값. 글꼴 요청에는 JetBrains Mono(`next/font`) 1개가 포함돼 있다.

| 페이지 | 현재(동적 서브셋) | A. 단일 서브셋 + preload + `optional` | B. 단일 서브셋 + `swap`(preload 없음) |
|---|---|---|---|
| 홈 | 요청 12개 272KB, FCP=LCP 2660ms | 2개 141KB, 2984ms (**+324**) | 2개 141KB, 2648ms |
| About | 17개 약 370KB, 2940ms | 2개 141KB, 3276ms (**+336**) | 2개 141KB, 2936ms |
| 글 상세 | 14개 349KB, 3384~3396ms | 2개 141KB, 3336ms (−60, 오차) | 2개 141KB, 3384ms |

- 모든 경우 CLS는 0이었다(1.4장).
- 개발은 "글꼴 파일 30개 이상"이라고 적었고 이 측정은 페이지당 11~17개다. 측정 조건이 다르다(개발은 Lighthouse 실행 기준으로 보인다).
- 서브셋: 사이트가 쓰는 글자 706자(한글 595자 + ASCII·기호)로 `PretendardVariable.woff2`(통짜 2.06MB)를 `fonttools`로 잘랐다. 가변 축 전체 140KB, 실제 쓰는 `wght 400–700`으로 제한하면 **102KB**다. 쓰는 한글은 전체 11,172자의 5.3%뿐이다.
- 디자인이 쓰는 굵기(display·h1 700, h2 700, h3·목록 제목 600, 본문 400)는 모두 400–700 안에 있다.

### 1.2 `optional`을 권하지 않는 이유

- **디자인 영향이 크다.** `optional`은 글꼴이 약 100ms 안에 오지 않으면 그 페이지에서는 끝까지 시스템 한글 글꼴로 보인다. 주 독자(J2, 모바일 검색 유입)는 대부분 첫 방문이라 캐시가 없다. 본문 17/1.8, 줄 길이, 제목 자간(−0.04em)은 Pretendard 기준으로 맞춘 값이라 시스템 글꼴에서는 달라진다.
- 동적 서브셋은 어느 조각이 필요한지 빌드 때 알 수 없어 preload할 수 없다. preload 없는 `optional`이면 대부분 폴백으로 끝난다(추정, 현재 구조에 `optional`을 적용한 측정은 하지 않았다).
- 단일 서브셋에 preload를 더해도(A) 홈·About에서 FCP·LCP가 330ms 안팎 느려졌다. preload가 CSS와 대역폭을 나눠 쓴 것으로 보인다(추정).

### 1.3 권장: B

- 빌드 때 `posts/`·`content/`·`src/`의 글자를 모아 Pretendard Variable을 서브셋한다. `wght 400–700`, woff2 단일 파일(약 102KB)을 자체 호스팅한다.
- `@font-face`는 `font-display: swap`, **preload는 하지 않는다.**
- 결과(측정): FCP·LCP는 현재와 같고, 글꼴 요청 12~17개 → 2개, 글꼴 용량 272~370KB → 141KB.
- 글자 모양은 같은 글꼴이라 그대로다.
- 글자 수집은 빌드마다 다시 한다. 새 글을 써도 빌드가 글자를 다시 모은다. 빠지는 글자가 있으면 그 글자만 `--font-sans`의 다음 글꼴(시스템)로 그려진다. 글이 늘어 글자가 늘면 파일이 커진다.
- PRD PR-15가 OG용으로 이미 한글 서브셋(제목 글자)을 요구하므로 글자 수집 로직을 같이 쓸 수 있다. 이번에는 `fonttools`(`pyftsubset`)로 시험했고 Node 도구는 시험하지 않았다. OG의 satori는 woff2를 읽지 못해(12번 E6) 파일 형식은 따로 필요하다.

### 1.4 CLS: 확인하지 못했다

- 이 환경(mac Chromium)은 현재 방식에서도 CLS가 0이라 개발이 본 리눅스 CI의 0.125~0.132를 재현하지 못했다. 그래서 **서브셋이 CLS를 푼다는 것은 검증하지 못했다.**
- 기대(추정): 지금은 조각 16개가 따로 도착하며 글꼴이 바뀌는데, 단일 파일이면 교체가 한 번으로 줄어든다.
- 서브셋 적용 후에도 CI의 CLS가 남으면 다음 단계는 폴백 글꼴 크기 보정(`size-adjust` 등)이다. 한글 폴백이 OS마다 달라 효과가 불확실하고, 리눅스 CI가 쓰는 폴백 글꼴의 실제 이름과 크기를 먼저 확인해야 한다.
- 그때까지 CLS는 `warn`으로 둔다(개발 P-18 그대로).
- **개발에 요청:** 서브셋 적용 PR에서 CI Lighthouse의 About CLS가 0.05 이하로 내려오는지 3회 중앙값으로 확인하고 `STATUS.md`에 적는다.

### 1.5 LCP

위 표에서 현재와 B의 FCP=LCP가 같다. 글꼴 방식을 바꿔도 LCP는 줄지 않는다. 텍스트가 폴백 글꼴로 먼저 그려지는 시점이 LCP이고, 그 시점은 CSS·JS 도착에 달려 있다. 렌더링 차단 CSS 2개와 JS 청크가 레버라는 개발의 분석은 이 측정과 모순되지 않는다(CSS·JS를 직접 확인하지는 않았다). 이 부분은 디자인 영향이 없어 요청하지 않는다.

## 2. 접근성 98→100

개발 작업 폴더의 로컬 Lighthouse 리포트(`.lighthouseci`, 리눅스 CI 결과가 아님) 기준으로 홈 0.96, 글(`bitnami-helm-chart-contribute`) 1.00, About 0.98이다. Q9에는 About만 적혀 있는데 **홈도 100이 아니다.**

| # | 페이지 | 감사 | 위치 | 원인 | 시안 | 개발 요청 |
|---|---|---|---|---|---|---|
| a | 홈 | `color-contrast` | 칩 숫자 `span.opacity-60`, `#58625d` on `#0c0f0e`, 12px, **3.05:1** | 구현은 `opacity-60`(3.05:1). **시안도** `.chip__count { opacity: 0.7 }`로 3.73:1이라 AA(4.5) 미달이었다 | `opacity` 제거로 수정함. `mute` 그대로 **6.53:1**, 선택된 칩 16.19:1 | `opacity-60` 제거 |
| b | 글 상세 | `label-content-name-mismatch` | `button.code__copy` | `aria-label="코드 복사"`인데 보이는 글자는 `copy`(WCAG 2.5.3 Label in Name). **시안도** 같았다 | `aria-label` 5곳 제거로 수정함. 이름 = 보이는 글자(`copy`/`copied`), 아이콘은 `aria-hidden` 유지 | `aria-label` 제거 |
| c | About | `heading-order` | `h2` 바로 아래 `h4`: "Schema Registry helm chart…"(Development Activities), "HashiCorp Certified…"(Certifications), "BoB 10기…"(Other Experience) | **구현 문제.** 시안 About은 `h1 h2 h2 h3 …`로 정상 | 변경 없음 | 항목 제목을 `h3`로. 시각 변화 없음(클래스로 스타일). 같은 컴포넌트를 쓰는 다른 곳도 확인 |

- b는 Lighthouse 점수에는 영향이 없다(글 상세가 1.00). 그래도 규칙 위반이라 고친다.
- 위 3건을 고치면 Lighthouse가 보는 3개 페이지의 접근성이 100이 될 것으로 **예상**한다. 재측정이 필요하다. 대비는 WCAG 공식으로 계산했고 Lighthouse의 값(3.05)과 같았다.
- **새 규칙**(`CONTEXT.md` 5장에 추가): ① 글자색을 `opacity`로 낮추지 않고 토큰을 쓴다(대비 4.5:1). ② 버튼의 접근 가능한 이름은 보이는 글자를 포함한다. ③ 제목 단계를 건너뛰지 않는다.
- 시안에서 글자에 `opacity`를 쓴 곳을 전부 찾았다. 실제 텍스트는 칩 숫자 하나뿐이고 `.path__sep`(`/`), `.tag::before`(`#`), 점선, 비활성 버튼은 장식이거나 검사 면제 대상이다.

## 3. 게이트 문구 (기획 결정)

- 디자인 의견: **현실화에 찬성한다.** 측정 조건을 문구에 적어야 한다. 예) "Lighthouse 모바일 기본 시뮬레이션(느린 4G, CPU 4배)".
- 근거: 이 측정의 에뮬레이션에서 가장 단순한 페이지도 FCP가 2.65~3.40s였다. 이 조건에서 LCP ≤ 2.0s는 CSS·JS를 크게 줄이지 않으면 어렵다. 참고로 Google Core Web Vitals의 "good" 기준은 실사용 75퍼센타일 LCP 2.5s다.
- 숫자는 기획이 정한다. 디자인은 제안하지 않는다.
